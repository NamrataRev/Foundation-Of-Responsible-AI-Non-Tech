## Overview

You have already built a pipeline that calls an AI model, searches document embeddings, and retrieves relevant lecture notes. Put together, when a student asks *"What is gradient descent?"*, the system finds the right notes and sends them to the model with the question.

That works. But consider what a student actually needs from an exam prep chatbot. They need an answer they can trust — one that is accurate, specific to their course material, and one they can verify against their notes if they want to.

The pipeline as built does not guarantee any of these three things. The model might add details that were never in the lecture notes. The student has no way to know whether the answer came from the retrieved notes or from the model's general training. And because whole lecture notes are retrieved as single chunks, a question about one specific concept pulls in an entire document — most of which is not relevant.

**RAG — Retrieval-Augmented Generation** is the pattern that makes AI answers trustworthy. It structures the pipeline so that every answer is grounded in specific retrieved documents, every claim can be traced back to its source, and the model is explicitly constrained to use only what was retrieved.

This topic explains what RAG is, why it exists, and how it addresses each of these problems. The files that follow implement each stage in full.

## What RAG Is — In Plain English

**RAG** stands for **Retrieval-Augmented Generation**. Before explaining the term, here is the plain English version.

Think of it like an open-book exam. In a closed-book exam, a student answers entirely from memory. They might misremember a formula, confuse two similar concepts, or confidently write something incorrect. In an open-book exam, the student finds the relevant page in their textbook, reads it, and bases their answer on what is written there. The examiner can verify the answer against the same page.

A plain LLM is the closed-book student — it answers from training data, which can be wrong, outdated, or unrelated to your specific course. RAG is the open-book approach — before generating an answer, the system finds the relevant documents and grounds the answer in them.

The three words in RAG name exactly what happens:

**Retrieve** — find the documents most relevant to the question. For the exam prep chatbot, this means comparing the student's question against all stored lecture notes, past papers, and model answers in ChromaDB, and returning the closest matches.

**Augment** — add the retrieved documents to the prompt as context. The model does not just see the question — it sees the question plus the specific sections of the lecture notes that are most likely to contain the answer.

To make this concrete — here is what the full augmented prompt actually looks like before it is sent to the model:

```text
SYSTEM: You are an exam preparation assistant. Answer using only
the lecture notes provided. Cite source IDs in square brackets.

CONTEXT (retrieved documents):
[ln_001] Gradient descent minimises the loss function by adjusting
parameters iteratively in the direction of steepest descent.

[ln_003] The learning rate controls the size of each parameter update
step. A high learning rate causes overshooting. A low learning rate
causes slow convergence.

QUESTION: What is the role of the learning rate in gradient descent?
```

The word "augmented" simply means the original prompt (system instructions + question) has been extended — augmented — with the retrieved documents. The model receives all three parts together as one input.

**Generate** — the model writes the answer using the retrieved context. Because the answer is based on specific documents, it is more accurate and can be traced back to its source.

## The Three Problems RAG Solves

### Problem 1 — Hallucination

A plain LLM generates text by predicting the most likely next word given everything it has seen so far. When it does not know something, it does not say "I do not know." It generates plausible-sounding text that may be factually wrong. This is called **hallucination** — the model producing confident, fluent, incorrect statements.

For the exam prep chatbot, this is dangerous. A student acting on a hallucinated answer could revise the wrong concept the night before an exam.

**How RAG reduces it:** when the retrieved lecture notes are in the context and the system prompt instructs the model to answer using only those notes, the model is constrained. It has specific, correct material in front of it. Hallucination is reduced — though not eliminated. The Why RAG Reduces Hallucination file covers the remaining failure cases.

### Problem 2 — No Grounding

Even when a plain LLM gives a correct answer, the student has no way to know whether it came from their course material or from something else the model learned during training. A fact that is generally true in the field might be explained differently in their specific course. Without grounding, the student cannot verify.

**How RAG fixes it:** because the retrieved documents are explicitly included in the prompt, and the model is instructed to cite its sources, every claim in the answer can be traced back to a specific document. The student sees `[ln_001]` next to a statement and can look up that exact lecture note.

### Problem 3 — Coarse Retrieval

When an entire lecture note is stored as one embedding vector, the vector represents the meaning of the whole document. A long note on backpropagation covers the chain rule, gradient flow, vanishing gradients, and weight initialisation. If a student asks specifically about vanishing gradients, the whole note is retrieved — most of it irrelevant. The relevant content is diluted.

**How RAG addresses it:** chunking breaks documents into smaller, focused pieces before embedding. Each chunk covers one idea. Retrieval then returns the specific chunk that matches the question — not the whole document. The Chunking Strategies file covers this in detail.

## RAG vs Fine-Tuning — Why Not Just Train the Model on the Notes?

A common question when first seeing RAG: why go through all this retrieval complexity? Why not just train — or fine-tune — the model on the lecture notes directly, so it already knows them?

**Fine-tuning** means taking a pre-trained model and continuing its training on a specific dataset. After fine-tuning on the lecture notes, the model would "know" the course material as part of its weights.

This sounds appealing but has three significant problems for the exam prep chatbot:

**It is expensive.** Fine-tuning a large language model requires significant compute, time, and money. It is not something a student project can run on demand.

**It is static.** Once fine-tuned, the knowledge is baked into the model weights. When lecture notes are updated at the start of a new semester, the model has to be fine-tuned again. With RAG, updating the knowledge base means adding new documents to ChromaDB — which takes seconds.

**It does not prevent hallucination.** Fine-tuning improves the model's familiarity with specific content, but the model still generates from learned patterns and can still hallucinate. RAG explicitly provides the correct text at inference time — which is a stronger constraint than learned knowledge.

| | RAG | Fine-tuning |
|---|---|---|
| **Cost** | Low — update ChromaDB with new documents | High — retrain the model |
| **Update speed** | Seconds — add new chunks to the index | Hours or days — retrain and redeploy |
| **Hallucination** | Reduced — correct text in context | Still possible — knowledge is in weights |
| **Citation** | Natural — source IDs come from retrieved chunks | Difficult — model does not know where it learned something |
| **Best for** | Dynamic knowledge bases, course notes, policies | Teaching the model a new style, format, or domain vocabulary |

For the exam prep chatbot — where notes change each semester and citation matters — RAG is the right choice. Fine-tuning would be the right choice if the goal was to teach the model to write in a specific academic style or respond in a particular format.

```text
Student question
        │
        ▼
  ┌─────────────┐
  │   RETRIEVE  │  ChromaDB compares the question vector
  │             │  against all stored document vectors
  │             │  Returns the 3 most similar chunks
  └──────┬──────┘
         │
         ▼
  ┌─────────────┐
  │   AUGMENT   │  Retrieved chunks added to the prompt:
  │             │  [ln_001] Gradient descent minimises...
  │             │  [ln_003] The learning rate controls...
  │             │  + the student's question
  └──────┬──────┘
         │
         ▼
  ┌─────────────┐
  │   GENERATE  │  Anthropic API generates an answer
  │             │  using only the retrieved chunks
  │             │  Cites source IDs in the answer
  └──────┬──────┘
         │
         ▼
Student receives:
"The learning rate controls the size of each parameter
update step [ln_003]. A high learning rate causes
overshooting [ln_003]..."
```

**Reading this diagram:**
- Each box is one stage — Retrieve, Augment, Generate
- The arrows show what passes between stages
- The output of Retrieve (chunks with IDs) becomes the input to Augment
- The output of Augment (the full prompt) becomes the input to Generate
- The output of Generate (the cited answer) goes back to the student

## What Changes With RAG — The Before and After

**Without RAG — plain LLM answer:**

```text
Student: "What is the role of the learning rate in gradient descent?"

Chatbot: "The learning rate is a hyperparameter that controls how quickly
the model learns. A typical value is 0.01. You can use learning rate
schedulers to reduce it over time."
```

This answer is not wrong — but it is generic, uses values not in the course notes, and mentions learning rate schedulers which may not be in the syllabus. The student cannot verify any of it.

**With RAG — grounded and cited answer:**

```text
Student: "What is the role of the learning rate in gradient descent?"

Chatbot: "The learning rate controls the size of each parameter update
step during gradient descent [ln_003]. A high learning rate causes
the algorithm to overshoot the minimum, preventing convergence [ln_003].
A low learning rate causes very slow convergence [ma_001].

Sources: ln_003 — Gradient Descent Notes, ma_001 — 2024 Model Answers"
```

Every claim has a source. The student can look up `ln_003` and verify the answer directly. Nothing in the answer goes beyond what the notes say.

## When RAG Is Not the Right Choice

RAG is powerful but it adds complexity. There are situations where it is the wrong tool:

**When the knowledge base is small enough to fit in the context window.** If the entire knowledge base is 10 short documents, passing all of them as context on every request is simpler and more reliable than building a retrieval pipeline. Retrieval adds value when the knowledge base is too large to include in full.

**When the knowledge base changes every few minutes.** ChromaDB needs to be updated whenever documents change. If the source data changes constantly — live news, real-time sensor data — maintaining a vector index is expensive and the index may always be slightly stale. Retrieval works best for knowledge bases that are updated periodically, not continuously.

**When exact keyword matching is what you need.** If a student searches for a specific equation number or a specific exam question by its code (e.g. "question 4b from 2024"), semantic search may return thematically related content rather than the exact match. For precise lookups, a traditional database search is more reliable than vector retrieval.

**When the answer requires reasoning across many documents simultaneously.** RAG retrieves the top-k most similar chunks. If the question requires synthesising information spread across 20 documents in a specific logical sequence, retrieval may not surface all of them or surface them in the right order. Simpler questions — "explain X", "what does Y mean" — are where RAG performs best.

## Worked Example — The Three Stages in Code

Here is a minimal version of all three stages together, showing how the exam prep chatbot flows from question to cited answer:

```python
from sentence_transformers import SentenceTransformer
import chromadb, os, requests
from dotenv import load_dotenv

load_dotenv()

# Setup — done once at startup
embed_model = SentenceTransformer("all-MiniLM-L6-v2")
client      = chromadb.PersistentClient(path="./exam_prep_db")
collection  = client.get_or_create_collection("exam_prep")

def rag_answer(question: str) -> str:

    # ── Stage 1: RETRIEVE ────────────────────────────────────────────
    query_vector = embed_model.encode([question]).tolist()
    results      = collection.query(query_embeddings=query_vector, n_results=3)

    if not results["documents"][0]:
        return "No relevant notes found for this question."

    # ── Stage 2: AUGMENT ─────────────────────────────────────────────
    context_parts = []
    for i, doc in enumerate(results["documents"][0]):
        doc_id = results["ids"][0][i]
        context_parts.append(f"[{doc_id}] {doc}")

    context = "\n\n".join(context_parts)
    # context now looks like:
    # [ln_001] Gradient descent minimises the loss function...
    # [ln_003] The learning rate controls the step size...

    # ── Stage 3: GENERATE ────────────────────────────────────────────
    response = requests.post(
        "https://api.anthropic.com/v1/messages",
        headers={"Content-Type": "application/json",
                 "x-api-key": os.environ.get("ANTHROPIC_API_KEY"),
                 "anthropic-version": "2023-06-01"},
        json={
            "model": "claude-sonnet-4-6",
            "max_tokens": 512,
            "system": "Answer using only the lecture notes provided. Cite source IDs in square brackets.",
            "messages": [{"role": "user",
                          "content": f"Notes:\n{context}\n\nQuestion: {question}"}]
        }
    )
    return response.json()["content"][0]["text"]


print(rag_answer("What is the role of the learning rate in gradient descent?"))
```

**Output**

```text
The learning rate controls the size of each parameter update step during
gradient descent [ln_003]. A high learning rate causes the algorithm to
overshoot the minimum [ln_003]. A low learning rate results in very slow
convergence [ma_001].
```

Each stage — Retrieve, Augment, Generate — maps directly to a labelled section of the code. The context string built in Stage 2 is the augmented prompt that Stage 3 sends to the model.

## Best Practices

- Always include the source document ID with every retrieved chunk — it is the foundation of citation at the generation stage
- Set a similarity threshold for retrieval — do not pass poor matches to the model as if they were relevant
- If retrieval returns nothing above the threshold, return a clear message instead of calling the model with empty context
- Keep the system prompt explicit about grounding: "answer using only the provided lecture notes" reduces hallucination more than a general instruction
- Test the pipeline end-to-end with questions that have no relevant match in the stored documents — verify the system handles this gracefully

## Common Beginner Mistakes

- **Skipping the retrieval step and passing all documents as context** — this works for small knowledge bases but fails as soon as documents exceed the context window. Retrieval is not optional.
- **Not checking whether retrieved documents are actually relevant** — the top-k results from ChromaDB are always returned, even when all of them are poor matches. A similarity threshold prevents poor context from reaching the model.
- **Assuming RAG eliminates hallucination** — it reduces it significantly, but the model can still drift beyond the retrieved context. The Why RAG Reduces Hallucination topic covers the specific cases where this happens.
- **Treating the generated citation as verified** — the model cites sources but may cite the wrong one. Citation accuracy requires a separate verification step, covered in the Citation and Grounding file.

## Key Takeaways

- **RAG** stands for Retrieval-Augmented Generation — a pattern that grounds AI answers in specific retrieved documents rather than general training data
- A plain LLM answers from memory and can hallucinate. RAG finds the relevant documents first and constrains the model to answer from them
- The three stages are: **Retrieve** (find relevant documents), **Augment** (add them to the prompt), **Generate** (write the answer using that context)
- RAG reduces hallucination by giving the model correct, specific material to draw from — but does not eliminate it entirely
- RAG enables grounding — every claim in the answer can be traced back to a specific retrieved document
- Chunking improves retrieval precision — smaller, focused chunks return more relevant content than whole documents
- The four files in this module implement each improvement: architecture, hallucination awareness, chunking, and citation

> **Interview tip:** If asked "what is RAG and why would you use it?" — describe the three stages, explain that a plain LLM answers from training data which can be wrong or outdated, and explain that RAG grounds answers in specific documents that can be verified. Name the three problems it solves: hallucination reduction, grounding, and retrieval precision. Most candidates describe RAG as just "adding documents to the prompt" — naming all three problems shows you understand why the pattern exists.
