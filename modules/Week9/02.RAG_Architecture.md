## Overview

The previous file introduced RAG as a pattern — Retrieve, Augment, Generate — and explained why it exists. This file implements each stage in full.

Understanding each stage properly is what separates a RAG pipeline that works in a demo from one that works reliably in production. A demo can afford to pass irrelevant documents as context, ignore context window limits, and hope the model cites correctly. A production system cannot.

This file goes through each stage one at a time — what it does, what the code looks like, and what specifically goes wrong if it is not implemented carefully. By the end, all three stages are connected into a working pipeline for the exam prep chatbot.

## Stage 1 — Retrieve

### What Retrieval Does

Retrieval is the first stage. Before the LLM sees the student's question, the system finds the most relevant documents from the knowledge base.

Think of it like a research assistant. Before a professor answers a student's question, they ask the assistant to pull the relevant pages from the filing cabinet. The professor does not search the entire cabinet themselves — the assistant does it quickly and hands over only what is needed.

For the exam prep chatbot:
- The student's question is converted to an embedding vector using the same model used to embed the documents
- ChromaDB compares that vector against all stored document vectors using cosine similarity
- The top matching documents are returned with their distance scores

**The critical detail:** both the question and the stored documents must have been embedded using the same model. A question embedded with `all-MiniLM-L6-v2` cannot be compared against documents embedded with `text-embedding-3-small` — the vectors live in different spaces and the distances would be meaningless.

```python
from sentence_transformers import SentenceTransformer
import chromadb

embed_model = SentenceTransformer("all-MiniLM-L6-v2")
client      = chromadb.PersistentClient(path="./exam_prep_db")
collection  = client.get_or_create_collection("exam_prep")

def retrieve(question: str, n_results: int = 3) -> list:
    """
    Convert the question to a vector and retrieve the n most similar documents.
    Returns a list of dictionaries — each with text, id, metadata, and distance.
    """
    query_embedding = embed_model.encode([question]).tolist()

    results = collection.query(
        query_embeddings=query_embedding,
        n_results=n_results
    )

    retrieved = []
    for i in range(len(results["documents"][0])):
        retrieved.append({
            "id":       results["ids"][0][i],
            "text":     results["documents"][0][i],
            "metadata": results["metadatas"][0][i],
            "distance": results["distances"][0][i]
            # distance: lower = more similar
            # 0.0 = identical meaning, 1.0+ = very different meaning
        })

    return retrieved


question = "What is the role of the learning rate in gradient descent?"
results  = retrieve(question, n_results=3)

for r in results:
    print(f"[{r['id']}] distance={r['distance']:.3f}")
    print(f"  {r['text'][:80]}...")
    print()
```

**Output**

```text
[ln_003] distance=0.312
  The learning rate controls the size of each parameter update step...

[ln_001] distance=0.441
  Gradient descent minimises the loss function by adjusting parameters...

[ma_001] distance=0.589
  A4b: A high learning rate causes overshooting. A low rate causes...
```

### What Can Go Wrong at Retrieval

**Wrong documents retrieved — retrieval precision problem.**
If the query and the document use very different vocabulary, the similarity score may be high (poor match) even when the content is conceptually relevant. This is addressed by chunking — covered in the Chunking Strategies file. Smaller, focused chunks produce more precise retrieval than whole documents.

**Poor match returned as if it were good.**
ChromaDB always returns the top-k results — even when all k of them are poor matches. A distance of 0.95 still gets returned if it is the closest thing in the index. Passing a poorly matched document to the LLM as context is worse than passing nothing — it actively misleads the model.

The fix is a **similarity threshold**:

```python
SIMILARITY_THRESHOLD = 0.8
# distance below 0.8 = relevant enough to use
# distance above 0.8 = too dissimilar — do not pass to the model

def retrieve_with_threshold(question: str, n_results: int = 3) -> list:
    results = retrieve(question, n_results)
    relevant = [r for r in results if r["distance"] < SIMILARITY_THRESHOLD]
    return relevant
    # returns an empty list if nothing is relevant enough
    # the caller handles the empty list — covered in Stage 3
```

**Too many results diluting the context.**
Retrieving 10 results when only 3 are needed fills the prompt with noise. The model's attention is spread across 10 chunks instead of focused on the 3 most relevant. Start with `n_results=3` and only increase if questions consistently require broader coverage.

## Stage 2 — Augment

### What Augmentation Does

Augmentation is the middle stage. The retrieved documents are combined with the student's question into a single prompt that gets sent to the LLM.

Think of it like preparing a briefing document. Before a manager answers a client's question, an assistant assembles the relevant background files into one clear document. The manager reads the briefing and answers from it — not from general memory.

The augmented prompt has three parts:

```text
SYSTEM INSTRUCTIONS
"You are an exam prep assistant. Answer using only the lecture notes
provided. Cite the source ID for each point you make."

RETRIEVED CONTEXT
[ln_003] The learning rate controls the size of each parameter update
step. A high learning rate causes overshooting.

[ln_001] Gradient descent minimises the loss function by adjusting
parameters iteratively in the direction of steepest descent.

[ma_001] A4b: A high learning rate causes overshooting. A low rate
causes slow convergence.

STUDENT QUESTION
"What is the role of the learning rate in gradient descent?"
```

All three parts together form the augmented prompt sent to the API.

```python
def augment(question: str, retrieved_docs: list) -> str:
    """
    Build the context string from retrieved documents.
    Each document is prefixed with its ID so the LLM can cite it.
    Returns an empty string if no documents were retrieved.
    """
    if not retrieved_docs:
        return ""

    # sort by distance — most relevant document first
    # LLMs pay more attention to content at the start of the context
    docs_sorted = sorted(retrieved_docs, key=lambda x: x["distance"])

    context_parts = []
    for doc in docs_sorted:
        context_parts.append(f"[{doc['id']}] {doc['text']}")

    return "\n\n".join(context_parts)


context = augment(question, results)
print(context)
```

**Output**

```text
[ln_003] The learning rate controls the size of each parameter update step. A high learning rate causes overshooting.

[ln_001] Gradient descent minimises the loss function by adjusting parameters iteratively in the direction of steepest descent.

[ma_001] A4b: A high learning rate causes overshooting. A low rate causes slow convergence.
```

### What Can Go Wrong at Augmentation

**Context window overflow.**
Every token in the prompt — system instructions, retrieved documents, and the question — counts toward the LLM's context window limit. If the retrieved documents are very long, the total may exceed the limit and the API returns an error.

```python
def count_tokens(text: str) -> int:
    """Rough estimate — 1 token per 0.75 words."""
    return len(text.split()) * 4 // 3

MAX_CONTEXT_TOKENS = 4000
# leaves room for system instructions and the question
# adjust based on the model's context window

def augment_within_limit(question: str, retrieved_docs: list) -> str:
    if not retrieved_docs:
        return ""

    docs_sorted   = sorted(retrieved_docs, key=lambda x: x["distance"])
    context_parts = []
    total_tokens  = 0

    for doc in docs_sorted:
        doc_text   = f"[{doc['id']}] {doc['text']}"
        doc_tokens = count_tokens(doc_text)

        if total_tokens + doc_tokens > MAX_CONTEXT_TOKENS:
            break   # stop adding documents once the limit is reached

        context_parts.append(doc_text)
        total_tokens += doc_tokens

    return "\n\n".join(context_parts)
```

**Not sorting by relevance.**
LLMs pay more attention to content at the beginning of the context. Putting the least relevant document first wastes the model's focus on low-value content. Always sort by distance before building the context string — the closest match first.

## Stage 3 — Generate

### What Generation Does

Generation is the final stage. The augmented prompt is sent to the LLM, which writes the answer.

Think of it like the professor reading the briefing and writing their response. They have the relevant material in front of them. A well-written answer draws directly from it. A poorly written answer drifts beyond it — adding things from general memory that were not in the briefing. That drift is hallucination, and it is the subject of the next file.

```python
from dotenv import load_dotenv
import os, requests

load_dotenv()

def generate(question: str, context: str) -> str:
    """
    Send the augmented prompt to the Anthropic API and return the generated answer.
    If context is empty — no relevant documents found — return a message instead
    of calling the API with nothing to ground the answer.
    """
    if not context:
        return (
            "I could not find relevant lecture notes for this question. "
            "Please check that the notes have been uploaded and indexed."
        )

    api_key = os.environ.get("ANTHROPIC_API_KEY")

    response = requests.post(
        "https://api.anthropic.com/v1/messages",
        headers={
            "Content-Type": "application/json",
            "x-api-key": api_key,
            "anthropic-version": "2023-06-01"
        },
        json={
            "model": "claude-sonnet-4-6",
            "max_tokens": 1024,
            "system": (
                "You are an exam preparation assistant for a BTech AI programme. "
                "Answer the student's question using only the lecture notes provided. "
                "For each point you make, cite the source in square brackets — for example [ln_001]. "
                "If the notes do not contain enough information, say so clearly rather than guessing."
            ),
            "messages": [
                {
                    "role": "user",
                    "content": f"Lecture notes:\n{context}\n\nQuestion: {question}"
                }
            ]
        }
    )

    response.raise_for_status()
    return response.json()["content"][0]["text"]
```

### What Can Go Wrong at Generation

**The LLM answers from training data despite the context.**
Sometimes an LLM ignores the provided context and answers from its general training — especially if the question is one it has seen many times. The system prompt instruction "answer using only the lecture notes provided" reduces this but does not eliminate it. The next file covers how to detect this.

**The LLM adds to the context.**
The model accurately reflects the retrieved notes but adds extra details from training that are not in the notes. These additions look correct and are fluent — making them hard to spot without a verification step. This is covered in the Citation and Grounding file.

**The answer is correct but the citation is wrong.**
The model might generate `[ln_002]` for a fact that actually came from `[ln_001]`. Citation accuracy is not guaranteed without verification.

## Putting It All Together — The Complete Pipeline

```python
from sentence_transformers import SentenceTransformer
from dotenv import load_dotenv
import chromadb, os, requests

load_dotenv()

embed_model = SentenceTransformer("all-MiniLM-L6-v2")
client      = chromadb.PersistentClient(path="./exam_prep_db")
collection  = client.get_or_create_collection("exam_prep")

SIMILARITY_THRESHOLD = 0.8
MAX_CONTEXT_TOKENS   = 4000

def retrieve(question: str, n_results: int = 3) -> list:
    query_embedding = embed_model.encode([question]).tolist()
    results = collection.query(query_embeddings=query_embedding,
                               n_results=n_results)
    retrieved = []
    for i in range(len(results["documents"][0])):
        retrieved.append({
            "id":       results["ids"][0][i],
            "text":     results["documents"][0][i],
            "distance": results["distances"][0][i]
        })
    return [r for r in retrieved if r["distance"] < SIMILARITY_THRESHOLD]

def augment(question: str, retrieved_docs: list) -> str:
    if not retrieved_docs:
        return ""
    docs_sorted   = sorted(retrieved_docs, key=lambda x: x["distance"])
    context_parts = []
    total_tokens  = 0
    for doc in docs_sorted:
        doc_text   = f"[{doc['id']}] {doc['text']}"
        doc_tokens = len(doc_text.split()) * 4 // 3
        if total_tokens + doc_tokens > MAX_CONTEXT_TOKENS:
            break
        context_parts.append(doc_text)
        total_tokens += doc_tokens
    return "\n\n".join(context_parts)

def generate(question: str, context: str) -> str:
    if not context:
        return "No relevant lecture notes found for this question."
    response = requests.post(
        "https://api.anthropic.com/v1/messages",
        headers={"Content-Type": "application/json",
                 "x-api-key": os.environ.get("ANTHROPIC_API_KEY"),
                 "anthropic-version": "2023-06-01"},
        json={
            "model": "claude-sonnet-4-6",
            "max_tokens": 1024,
            "system": (
                "Answer using only the lecture notes provided. "
                "Cite source IDs in square brackets for each point."
            ),
            "messages": [{"role": "user",
                          "content": f"Notes:\n{context}\n\nQuestion: {question}"}]
        }
    )
    response.raise_for_status()
    return response.json()["content"][0]["text"]

# ── Full pipeline ────────────────────────────────────────────────────
question = "What is the role of the learning rate in gradient descent?"

retrieved = retrieve(question)           # Stage 1 — Retrieve
context   = augment(question, retrieved) # Stage 2 — Augment
answer    = generate(question, context)  # Stage 3 — Generate

print(answer)
```

**Output**

```text
The learning rate controls the size of each parameter update step
during gradient descent [ln_003]. A high learning rate causes the
algorithm to overshoot the minimum — the loss bounces rather than
converging [ln_003]. A low learning rate causes very slow convergence,
making training unnecessarily long [ma_001].
```

Each function maps directly to one RAG stage. The output of `retrieve()` feeds `augment()`. The output of `augment()` feeds `generate()`. The final answer contains citations the student can verify.

## Best Practices

- Use the same embedding model for both indexing documents and embedding queries — mixing models produces meaningless distance scores
- Always set a similarity threshold — never pass poor matches to the model as if they were relevant
- Sort retrieved documents by distance before building the context — most relevant document first
- Handle the empty context case explicitly — return a clear message rather than calling the API with nothing to ground the answer
- Count tokens before building the context — stop adding documents when the limit is reached rather than letting the API return an error

## Common Beginner Mistakes

- **Mixing embedding models** — querying with `all-MiniLM-L6-v2` against documents indexed with `text-embedding-3-small` produces wrong distances. One model throughout.
- **Not using a similarity threshold** — always retrieving top-k regardless of match quality passes irrelevant context to the model, actively making answers worse
- **Not handling empty retrieval** — if `retrieve()` returns an empty list and `generate()` is called with no context, the model answers from general training — hallucination with no grounding
- **Ignoring context window limits** — long retrieved documents can overflow the model's context window and cause an API error. Count tokens and stop early
- **Assuming citation accuracy** — the model may cite the wrong source even when the content is correct. Verification is covered in the Citation and Grounding file

---

## Key Takeaways

- **Retrieval** converts the question to a vector, compares it against stored document vectors, and returns the closest matches — using the same embedding model used to index documents
- A **similarity threshold** prevents poor matches from reaching the model — always filter by distance before augmenting
- **Augmentation** combines retrieved documents with the question into one prompt — sort by relevance and stay within the context window limit
- **Generation** sends the augmented prompt to the LLM — handle the empty context case before calling the API
- Each stage has specific failure modes — precision problems in retrieval, overflow in augmentation, hallucination and citation errors in generation
- The three functions — `retrieve()`, `augment()`, `generate()` — map directly to the three RAG stages and connect sequentially

> **Interview tip:** If asked "how would you implement a RAG pipeline?" — name all three stages and for each one describe one thing that can go wrong and how you handle it. Mention the similarity threshold, the context window limit, and the empty context fallback. Most candidates describe RAG as retrieve-then-generate without the failure handling — showing you know what breaks in production sets you apart.
