## Overview

The RAG Architecture topic built the three-stage RAG pipeline — Retrieve, Augment, Generate. The generated answers include citations and are grounded in retrieved lecture notes. This is already a significant improvement over a plain LLM.

But a common misconception among developers first learning RAG is that retrieval solves hallucination. It does not. It reduces it — significantly in some cases, barely in others.

A student using the exam prep chatbot needs to be able to trust the answer. If the chatbot says gradient descent uses a learning rate of 0.001, is that from the lecture notes or did the model add it? If it says backpropagation was first proposed in 1986, is that correct? If it says "according to your notes, the loss function must always be convex", and the notes say no such thing — how does the student know?

This file explains what hallucination actually is at the model level, why RAG reduces it, and — critically — the specific situations where a RAG system can still produce wrong answers. Every developer building with LLMs needs to understand both sides of this.

## What Hallucination Is

### The Plain English Definition

**Hallucination** is when an LLM generates text that is factually incorrect, unsupported by its sources, or simply made up — while presenting it with the same confidence as accurate information.

The word "hallucination" is used because the model does not know it is wrong. It is not lying. It is not guessing and hoping. It generates what it calculates to be the most likely next token — and sometimes that most likely next token is factually incorrect.

Think of it like a student who has studied a subject for weeks but is exhausted during the exam. They remember the general shape of an answer but fill in the specific details from memory — and some of those details are subtly wrong. They write confidently because they do not notice the error. That is hallucination.

### Why It Happens — The Technical Reason

An LLM does not store facts the way a database stores records. It learns statistical patterns from billions of text examples. When generating an answer, it is essentially asking: "given everything I have seen, what text is most likely to follow this prompt?"

This works well for common, well-represented topics. But it fails in three specific situations:

**When the training data contained conflicting information.** If different sources in the training data give different values for the same fact — different textbooks defining the same concept differently — the model averages across them and may produce a blend that matches none exactly.

**When specific details are rare in the training data.** The model may know a concept well but have seen few examples of a specific numerical value or precise definition. It generates a plausible-sounding value rather than nothing.

**When the model is asked about specific, local knowledge.** Your university's specific course notes, your professor's specific way of defining a term, your exam board's specific notation — none of this was in the training data. The model fills in from general knowledge, which may not match.

## Why RAG Reduces Hallucination

RAG reduces hallucination through one core mechanism: **it gives the model correct, specific text to draw from at the moment of generation.**

Instead of relying on learned statistical patterns, the model has the actual lecture notes in its context. The system prompt tells it to use only those notes. The path of least resistance for the model is to draw from what is right there — which happens to be correct.

### Mechanism 1 — Correct Text in Context

When `[ln_003]` contains *"The learning rate controls the size of each parameter update step"*, and the model is told to answer from the notes, the most likely completion of the answer involves the text already in context. The model echoes and paraphrases the retrieved content rather than generating from general patterns.

### Mechanism 2 — Constraint Through the System Prompt

The instruction *"answer using only the lecture notes provided"* creates a constraint. The model is explicitly told not to go beyond the context. This does not eliminate the possibility — but it shifts the model's behaviour toward retrieval-grounded generation.

### Mechanism 3 — Citation as a Self-Check

When the model is asked to cite its sources, it must map each claim to a specific document. This process implicitly checks whether the claim exists in the retrieved context. Claims that have no source to cite are less likely to appear — because the model cannot find a document to cite them from.

## Where RAG Does Not Prevent Hallucination

This is the part most tutorials skip. RAG reduces hallucination but does not eliminate it. Here are the five specific situations where a RAG pipeline can still produce wrong answers:

### Failure 1 — The Retrieved Documents Are Wrong

RAG can only be as accurate as the documents it retrieves. If the lecture notes themselves contain an error — a wrong formula, an outdated value, a typo — the model will reproduce that error faithfully. This is not hallucination in the model but it is still a wrong answer.

**For the exam prep chatbot:** if `ln_001` contains a typo that says the loss function is *maximised* instead of minimised, the chatbot will confidently tell every student that gradient descent maximises the loss function — and cite `ln_001` as the source.

**What to do:** the knowledge base itself must be reviewed. RAG does not verify the quality of the source documents.

### Failure 2 — The Model Ignores the Context

Sometimes the model answers from its general training even when relevant context is provided. This is most common when:
- The question is one the model has seen very frequently in training (e.g. "what is gradient descent?") — it defaults to its standard answer
- The retrieved context is long and the relevant section appears far from the beginning — the model's attention is diluted
- The system prompt is weak — "use the notes if you can" gives the model too much latitude

```text
Student: "What is backpropagation?"

Retrieved context: [ln_002] Backpropagation computes gradients layer by
layer using the chain rule, starting from the output layer.

Chatbot: "Backpropagation is the algorithm used to train neural networks
by calculating the gradient of the loss with respect to each weight using
the chain rule. It was first described by Rumelhart, Hinton, and Williams
in 1986."
```

The date 1986 was not in the lecture notes. The model added it from general training. The answer sounds complete and confident — and it is mostly correct — but the chatbot has gone beyond what the notes say.

**What to do:** strengthen the system prompt. *"Answer using only the lecture notes provided. Do not add any information that is not explicitly stated in the notes."* is more constraining than a general instruction.

### Failure 3 — The Model Fills Gaps Between Retrieved Chunks

When the answer requires connecting two pieces of information — and that connection is not explicitly stated in either retrieved chunk — the model may infer the connection itself. The inference may be wrong.

```text
Retrieved chunk 1: "A high learning rate causes overshooting."
Retrieved chunk 2: "Overshooting prevents the loss from converging."

Model generates: "Therefore, a learning rate above 0.1 will always
prevent convergence." [fabricated threshold]
```

Neither chunk mentioned 0.1. The model combined the two true statements and added a specific threshold that was never stated. The generated claim cites the source documents — but the specific value is hallucinated.

**What to do:** chunking strategy helps here. If the specific threshold exists in the notes, it should be in the same chunk as the overshooting explanation. The Chunking Strategies file covers this.

### Failure 4 — The Model Cites the Wrong Source

The model may generate a correct answer drawn from one document but cite a different document as the source. The answer is accurate; the citation is wrong.

```text
Fact from [ln_001]: "Gradient descent is an iterative optimisation algorithm."
Fact from [ln_003]: "The learning rate controls step size."

Model generates: "The learning rate controls step size [ln_001]."
```

`ln_001` did not say this. `ln_003` did. The content is correct but the citation is inaccurate.

**What to do:** verified citation requires a separate check — covered in the Citation and Grounding file.

### Failure 5 — Confident Language Masking Uncertainty

The model generates with consistent confidence regardless of how certain it actually is. When the retrieved notes contain vague or incomplete information, the model may produce a precise-sounding answer that goes beyond what the notes support.

```text
Notes say: "Dropout is a regularisation technique used to prevent
overfitting in neural networks."

Model generates: "Dropout should typically be applied with a rate of
0.5 for hidden layers and 0.2 for input layers."
```

The notes said nothing about specific dropout rates. The model generated specific values because the question seemed to call for them — and those values are generally reasonable — but they are not from the notes.

**What to do:** instruct the model explicitly about uncertainty: *"If the notes do not provide specific values or details, say 'the notes do not specify this' rather than providing a general answer."*

## Real Cases — When Hallucination Has Consequences

Understanding hallucination becomes more urgent when you see what it costs in the real world.

**Air Canada chatbot — 2024.** Air Canada deployed a customer support chatbot that told a passenger he could apply for a bereavement fare discount after travel and claim a refund retroactively. This was false — Air Canada's policy required the discount to be applied before travel. The passenger relied on the chatbot, paid full price, and was denied the refund. Air Canada argued in court that the chatbot was a "separate legal entity" responsible for its own statements. The tribunal rejected this and held Air Canada liable. The airline was ordered to pay the passenger the difference.

📎 [Air Canada chatbot ruling — CBC News](https://www.cbc.ca/news/canada/british-columbia/air-canada-chatbot-ruling-1.7116416)

**What this means for the exam prep chatbot.** A student who revises the wrong concept the night before an exam because the chatbot hallucinated has failed in a way that cannot be undone. The stakes are lower than a legal case — but the principle is identical. A confident, fluent, wrong answer is worse than no answer at all. This is why the strategies in this topic — strong system prompts, low temperature, verification — are not optional polish. They are what makes an AI-powered tool trustworthy.

## Practical Strategies — Reducing Hallucination in the Exam Prep Chatbot

### Strategy 1 — Strengthen the System Prompt

Weak system prompt:
```text
"Answer the student's question using the lecture notes."
```

Strong system prompt:
```text
"Answer using only the information explicitly stated in the lecture notes
provided. Do not add information from general knowledge. If the notes
do not contain enough detail to answer the question fully, say exactly
what the notes do say and note what is missing."
```

### Strategy 2 — Temperature Control

Lower temperature reduces the model's tendency to generate creative or unexpected completions. For factual recall from lecture notes, a temperature of 0.1 to 0.3 is appropriate.

```python
json={
    "model": "claude-sonnet-4-6",
    "max_tokens": 1024,
    "temperature": 0.1,   # low temperature — stick close to the most likely completion
    "system": "Answer using only the lecture notes provided...",
    "messages": [...]
}
```

### Strategy 3 — Ask the Model to Flag Uncertainty

```python
system_prompt = (
    "You are an exam preparation assistant. "
    "Answer using only the lecture notes provided. "
    "If the notes do not contain enough information to answer fully, "
    "state what the notes do say and explicitly note: "
    "'Note: the provided notes do not cover this in detail.' "
    "Never add information from general knowledge."
)
```

### Strategy 4 — Post-Generation Verification

After the answer is generated, ask the model to check its own answer against the retrieved context:

```python
def verify_answer(answer: str, context: str) -> str:
    """
    Ask the model to check whether the generated answer
    is fully supported by the retrieved context.
    """
    api_key  = os.environ.get("ANTHROPIC_API_KEY")
    response = requests.post(
        "https://api.anthropic.com/v1/messages",
        headers={
            "Content-Type": "application/json",
            "x-api-key": api_key,
            "anthropic-version": "2023-06-01"
        },
        json={
            "model": "claude-sonnet-4-6",
            "max_tokens": 512,
            "system": (
                "You are a fact-checker. Given a generated answer and the "
                "source notes it was based on, identify any claims in the "
                "answer that are not explicitly supported by the notes. "
                "List each unsupported claim on its own line. "
                "If all claims are supported, respond with: 'All claims supported.'"
            ),
            "messages": [
                {
                    "role": "user",
                    "content": f"Source notes:\n{context}\n\nGenerated answer:\n{answer}"
                }
            ]
        }
    )
    return response.json()["content"][0]["text"]
```

**Output** (for the dropout example above):

```text
Unsupported claim: "Dropout should typically be applied with a rate of
0.5 for hidden layers and 0.2 for input layers." — the notes do not
specify dropout rates.
```

The verification step uses the model to check the model. It is not perfect — but it catches the most obvious cases where the answer has drifted beyond the notes.

## Best Practices

- Never assume RAG eliminates hallucination — it reduces it. Always design with the assumption that some answers will be wrong
- Use a low temperature (0.1–0.3) for factual retrieval tasks — this reduces creative completion and keeps answers closer to the retrieved text
- Write explicit system prompts that instruct the model about uncertainty — "if the notes do not say, say so" is more effective than a general instruction to use the notes
- Add a post-generation verification step for high-stakes answers — having the model check its own answer against the context catches the most obvious failures
- Review the source documents — RAG cannot fix errors in the knowledge base itself

## Common Beginner Mistakes

- **Assuming a citation means the claim is correct** — the model can cite the wrong document, or cite a document that does not support the specific claim made
- **Using a high temperature for factual tasks** — higher temperature increases creativity and increases hallucination. For exam prep, keep temperature low
- **Not instructing the model about uncertainty** — without explicit instruction, the model fills gaps with plausible-sounding content rather than admitting what the notes do not cover
- **Trusting a confident tone** — LLMs always sound confident. A hallucinated answer and a correct answer are written in the same style. Confidence is not a signal of accuracy

## Key Takeaways

- **Hallucination** is when an LLM generates factually incorrect or unsupported content — it happens because the model generates from statistical patterns, not from a verified fact store
- **RAG reduces hallucination** through three mechanisms: correct text in context, constraint through the system prompt, and citation as a self-check
- RAG does **not** prevent hallucination in five specific situations: wrong source documents, model ignoring context, model filling gaps between chunks, wrong citation, and confident language masking uncertainty
- The most effective mitigations are: a strong explicit system prompt, low temperature, uncertainty flagging, and post-generation verification
- **The knowledge base itself must be reviewed** — RAG cannot fix errors in the source documents

> **Interview tip:** If asked "does RAG solve hallucination?" — never say yes. Say it significantly reduces it through specific mechanisms — correct text in context, system prompt constraint, citation as a self-check — and then name two or three situations where it still fails. Most candidates say "RAG fixes hallucination." Knowing the specific failure modes shows you understand the limits of the pattern, which is what production engineering requires.
