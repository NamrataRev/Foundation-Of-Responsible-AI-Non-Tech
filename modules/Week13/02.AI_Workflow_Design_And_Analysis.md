## Part 1 — The End-to-End AI-Assisted Workflow

### The Five-Stage Professional Workflow

Every domain-specific RAG application follows the same five stages. The domain changes what happens at each stage — not the stages themselves.

```text
STAGE 1 — QUESTION INTAKE
The user types a question in the Pinecone playground.
Domain-specific: the question uses domain terminology and references
domain concepts. A civil engineer asks about IS code clauses.
A pharma student asks about drug interactions.

STAGE 2 — RETRIEVAL
Pinecone converts the question to a vector and searches the
uploaded domain documents for the most relevant chunks.
Domain-specific: the chunks come from IS codes, IRC standards,
course notes — not from the internet.

STAGE 3 — AUGMENTATION
Retrieved chunks are combined with the question and system prompt
into one prompt sent to Claude.
Domain-specific: the system prompt instructs Claude to answer
only from the uploaded standards and to cite clause numbers.

STAGE 4 — GENERATION
Claude generates a cited answer using only the retrieved chunks.
Domain-specific: the answer includes IS code clause references,
table numbers, and the specific values from the uploaded documents.

STAGE 5 — HUMAN VERIFICATION
The user reads the answer, clicks the cited source, and verifies
the claim against the actual IS code clause.
Domain-specific: for high-stakes design decisions, the engineer
verifies the full clause before acting on the answer.
```

### The Civil Engineering Workflow — Applied

Here is what the five stages look like specifically for the civil engineering knowledge assistant:

```text
STAGE 1 — QUESTION INTAKE
Civil engineer types:
"What is the minimum clear cover required for reinforcement in a
column exposed to moderate environmental exposure?"

STAGE 2 — RETRIEVAL
Pinecone searches uploaded documents:
- IS 456 (Clause 26.4 — Cover to reinforcement)
- Course notes on durability requirements
Returns top 3 chunks — IS 456 Table 16 chunk is most similar

STAGE 3 — AUGMENTATION
Prompt sent to Claude:
"[IS 456 Table 16] For moderate exposure, the minimum cover for
columns is 40mm...
[Course notes] Environmental exposure classification — moderate
means...
Question: What is the minimum clear cover for a column in
moderate exposure?"

STAGE 4 — GENERATION
Claude generates:
"According to IS 456 Table 16 [Source 1], the minimum clear
cover for a column in moderate environmental exposure is 40mm.
Your course notes define moderate exposure as... [Source 2]"

STAGE 5 — HUMAN VERIFICATION
Engineer clicks [Source 1] — IS 456 Table 16 chunk appears.
Engineer confirms: the value 40mm appears in the chunk.
Engineer uses the value in their design calculation.
```

## Part 2 — Where AI Helps and Where It Fails

### Where AI Genuinely Helps in Domain Applications

**Help 1 — Searching across multiple documents simultaneously**
A civil engineer designing a reinforced concrete column needs IS 456 (concrete), IS 800 (if composite with steel), IS 1893 (earthquake zone), and IRC standards (if it is a bridge column). Manual search across four documents for one design decision takes 20-30 minutes. RAG retrieves the relevant clauses from all four simultaneously in seconds.

**Help 2 — Surfacing connections between standards**
A question about "minimum column dimension" may have answers in IS 456 (structural), NBC (building regulations), and state PWD specifications (local requirements). RAG can surface all three if all three are uploaded. A manual search might miss one.

**Help 3 — Translating technical questions into plain language**
A student who does not know the exact IS code clause can ask in plain language — "how thick should my slab be for a residential building?" — and RAG finds the relevant IS 456 guidance without requiring the student to know the clause number in advance.

**Help 4 — Consistent answers across multiple users**
If 50 junior engineers in a firm all need to know the same IS code requirement, a domain-specific RAG application gives all 50 the same answer from the same source — rather than 50 individuals searching and potentially finding different interpretations.

### Where AI Fails in Domain Applications

**Failure 1 — Calculations**
RAG retrieves text. It does not calculate. If a civil engineer asks "what is the moment capacity of this beam?", the chatbot can retrieve the formula from IS 456 and the material properties from the uploaded notes — but it cannot run the calculation. The engineer must apply the formula themselves.

**What to do:** the system prompt should explicitly state: "Do not perform calculations. Provide the relevant formula and values from the notes. The user must apply the formula."

**Failure 2 — Interpretation of ambiguous clauses**
IS codes sometimes have clauses that require professional interpretation — where the clause is written for the general case but the specific situation has factors not addressed. RAG retrieves the clause but cannot apply professional engineering judgment to interpret it for the specific case.

**What to do:** for questions requiring interpretation — not just retrieval — the chatbot should flag that professional judgment is needed: "IS 456 Clause 26.4 applies to this situation [Source 1], but the specific case of [X] may require interpretation by a licensed structural engineer."

**Failure 3 — Outdated documents**
If IS 456 is revised and the uploaded document is the old version, the chatbot answers from the outdated standard. It has no way to know the document is outdated.

**What to do:** the consent notice and system prompt should state the version of each uploaded document. The Pinecone assistant should be re-indexed when new versions are published.

**Failure 4 — Questions that span uploaded and non-uploaded standards**
A civil engineer asks about seismic design for a bridge. IS 1893 (uploaded) covers buildings. IRC 6 (not uploaded) covers bridges. The chatbot retrieves IS 1893 and answers as if it applies to bridges — because it does not know IRC 6 exists.

**What to do:** the system prompt should state: "If the question concerns [specific domain areas], note that the relevant standard [document name] has not been uploaded and the answer may be incomplete."

### The Civil Engineering Failure Mode Table

| Question type | AI reliable? | Human verification required? |
|---|---|---|
| "What does clause X say?" | ✅ High reliability | Spot-check citation |
| "What value does Table Y give for condition Z?" | ✅ High reliability | Click citation, confirm value |
| "Which clause applies to this situation?" | ⚠️ Medium — depends on how clearly the situation matches the clause | Read the full clause, not just the retrieved chunk |
| "Calculate the capacity of this member" | ❌ AI should not calculate | Engineer applies formula from retrieved clause |
| "Interpret this clause for my specific case" | ❌ Requires professional judgment | Licensed engineer reviews |
| "Is this design compliant with all relevant standards?" | ❌ Chatbot only knows uploaded standards | Engineer checks all applicable standards |

## Part 3 — The HITL Model for Your Domain Application

### Applying the Three Models to Civil Engineering

The three oversight models from the Human-in-the-Loop Design topic apply directly to the civil engineering knowledge assistant. The stakes and reliability of each question type determine which model applies.

**Model 1 — Human Always Verifies**
Applied to: questions whose answers directly influence a structural design decision — beam dimensions, reinforcement ratios, material specifications, load calculations.

```text
Civil engineer asks: "What is the permissible bending stress for
Fe 415 steel in the Working Stress Method?"

Chatbot answers: "According to IS 456 Annex B [Source 1], the
permissible stress in bending for Fe 415 steel is 230 N/mm²."

Human verification required:
Engineer clicks [Source 1]. Reads the actual IS 456 Annex B entry.
Confirms 230 N/mm². Only then uses this value in design calculations.

Why Model 1: a wrong value here could mean an under-designed
structure. The cost of one wrong answer is potentially catastrophic.
```

**Model 2 — Human Verifies Exceptions**
Applied to: reference questions that inform understanding but do not directly drive a design value — definitions, explanations, background concepts.

```text
Civil engineer asks: "What is the difference between working stress
method and limit state method?"

Chatbot answers: "The Working Stress Method assumes linear elastic
behaviour and uses permissible stresses [Source 1]. The Limit State
Method considers collapse and serviceability limit states [Source 2]."

Human verification: click citations if the explanation will be
used in a report or assignment. Accept directly for general
understanding during study.

Why Model 2: the cost of a wrong explanation is confusion, not
structural failure. Medium stakes — verify when the answer will
be acted on formally.
```

**Model 3 — Periodic Audit**
Applied to: general study questions used for revision — terminology, definitions, conceptual questions with no direct design implication.

```text
Civil engineer asks: "What is the definition of characteristic
strength in IS 456?"

Chatbot answers: "Characteristic strength is the value of strength
below which not more than 5% of test results are expected to fall
[Source 1]."

Human verification: once a week, audit 5 random answers from
this category. No individual verification required.

Why Model 3: the cost of a wrong definition during revision is
negligible. Low stakes — periodic auditing is sufficient.
```

## Part 4 — The Regulatory Map

### Applying the Three Frameworks to the Civil Engineering Application

Every domain application must be classified under the three regulatory frameworks from Week 12. Here is how the civil engineering knowledge assistant maps to each.

**EU AI Act Classification**

| Question | Answer |
|---|---|
| What tier? | **Limited Risk** — it is a chatbot providing information |
| Would it be High Risk? | Yes, if it made autonomous structural design decisions that engineers acted on without review. As an information retrieval tool, it is Limited Risk. |
| Primary obligation | Transparency disclosure — users must know they are interacting with AI |
| Does GPAI apply? | Yes — Claude is a GPAI model. Anthropic's obligations as provider are separate from the deployer's obligations. |
| What the deployer must do | Add a disclosure: "This is an AI-powered reference tool. All values must be verified against the original IS code before use in structural design." |

**NIST AI RMF Mapping**

| Function | What it means for the civil engineering assistant |
|---|---|
| **Govern** | Who is responsible for maintaining the knowledge base? Who approves adding new IS codes? Who handles a complaint that the chatbot gave a wrong clause value? |
| **Map** | Affected population: civil engineering students and junior engineers. Risk: wrong IS code value leads to design error. Misuse: treating chatbot output as a substitute for reading the actual clause. |
| **Measure** | Golden dataset: 10 questions from IS 456 with verified correct clause references. Reliability target: 90%+ correct citations on direct clause questions. |
| **Manage** | Weekly golden dataset evaluation. If reliability drops below 90%, re-index documents and investigate. If a wrong value is reported by a user, document and fix within 24 hours. |

**DPDP Act Obligations**

| Data type | DPDP status | Obligation |
|---|---|---|
| Student name and email (login) | Personal data | Collect minimum necessary, consent required |
| Uploaded IS codes (public documents) | Not personal data | No DPDP obligation |
| Uploaded course notes (if they contain student's own name) | Potentially personal data | Consent notice should cover this |
| Question history linked to account | Personal data (indirect) | Retention policy required, deletion on request |

**For the civil engineering assistant at a university:** DPDP applies primarily to the student login data and question history. IS codes themselves are public documents with no personal data. The DPDP compliance checklist from Week 12 applies in full.

## Best Practices

- Complete the workflow template on paper before opening Pinecone — building without a design means making decisions you have not thought through
- Be honest about where AI fails in your domain — the failure analysis is what determines the oversight model, which is what makes the application trustworthy
- The regulatory map is not optional — every deployed AI application has regulatory obligations. Identifying them before deployment is required; discovering them after deployment is a problem
- When in doubt about the oversight model — apply the higher one. Model 1 costs more time; a wrong answer in a high-stakes domain costs more than time

## Common Beginner Mistakes

- **Designing a workflow where AI is the final authority** — in every professional domain, a human must verify AI output before it is acted on. If your design has no human verification step, the oversight model is wrong
- **Skipping the failure analysis** — the temptation is to show where AI helps and skip where it fails. The failure analysis is what makes the design credible
- **Leaving the regulatory map blank** — "I am not sure which laws apply" is not an acceptable answer. Use Week 12 to classify your application. If genuinely uncertain, state the uncertainty and name the frameworks that might apply

## Key Takeaways

- The five-stage professional workflow — Question Intake, Retrieval, Augmentation, Generation, Human Verification — applies to every domain
- For civil engineering: AI reliably retrieves IS code clause values but cannot calculate, interpret ambiguous clauses, or cover standards that were not uploaded
- The HITL model depends on the stakes of a wrong answer — structural design values require Model 1, general study questions allow Model 3
- Every domain application must be classified under EU AI Act (likely Limited Risk), NIST AI RMF (four functions applied), and DPDP (personal data obligations)
- The design document — workflow, failure analysis, HITL model, regulatory map — is A4 Component 1

> **Interview tip:** If asked "how would you design an AI system for professional use in your domain?" — describe the five-stage workflow, name two specific places where AI fails in that domain, state which HITL model applies to high-stakes decisions and why, and name the regulatory frameworks that apply. Most candidates describe the AI capabilities only. Describing the failure modes, the oversight model, and the regulatory obligations shows you understand professional AI deployment as an engineering discipline with safety and compliance requirements.
