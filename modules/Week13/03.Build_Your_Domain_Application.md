# Build Your Domain Application

---

## Learning Objectives

By the end of this topic, you should be able to:

- Upload domain-specific documents to Pinecone and configure the assistant correctly
- Write a domain-specific system prompt that constrains answers to uploaded documents
- Build and run a golden dataset evaluation for your domain
- Document the results and produce the A4 submission

## Step 1 — Prepare Your Domain Documents

### What to Upload

The quality of the application depends entirely on what is uploaded. Review your problem statement from File 1. The documents you named there are what go into Pinecone.

**For the civil engineering assistant — upload these:**
- IS 456 (or the relevant chapters — plain and reinforced concrete)
- IS 800 (structural steel — if in scope)
- IS 1893 (earthquake design — if in scope)
- Course lecture notes on structural analysis
- Course lecture notes on the design methodology your lecturer uses
- Past exam papers with model answers

**For your domain — upload:**
Whatever you named in your File 1 problem statement. If you have not named specific documents, do that now before uploading anything.

### Before Uploading — Three Checks

**Check 1 — Do you own or have permission to use this document?**
IS codes and IRC standards are published by BIS and IRC respectively. They are available for purchase and download through official channels. Uploading a legitimately obtained copy is acceptable. Uploading a pirated scan is copyright infringement.

Course lecture notes you wrote yourself are yours to upload. Your lecturer's slides are their intellectual property — check whether your institution permits uploading them to third-party AI tools.

**Check 2 — Is the document the current version?**
IS 456 was last revised in 2000. IS 800 was revised in 2007. Check that the document version matches what your course uses and what the current standard is.

**Check 3 — Does the document contain personal data?**
If course notes contain real student names, patient names (for healthcare), or client names (for legal/finance) — remove or anonymise that information before uploading. Review the DPDP checklist from Week 12.

### Structuring Documents for Better Retrieval

Pinecone chunks documents at natural boundaries. Documents with clear headings, section numbers, and paragraph breaks produce better chunks than continuous text.

**For IS codes:** the standard is already well-structured with numbered clauses. Upload as-is — Pinecone will chunk by section.

**For lecture notes:** if your notes are a wall of text without headings, add headings before uploading. "Section 1 — Working Stress Method" as a heading produces a better chunk boundary than no heading at all.

**The one-topic-per-file principle:** if you have notes covering five different topics in one long document, consider splitting into five files before uploading. Retrieval is more precise when each file covers one focused topic.

## Step 2 — Configure Pinecone Assistant

Follow the exact steps from the RAG Architecture topic. Here is the complete setup sequence:

**2.1 — Sign in to Pinecone**
Go to **app.pinecone.io** and sign in to your account.

**2.2 — Create or open your assistant**
- If you already have `exam-prep-chatbot` from the RAG module — create a new assistant for your domain application. Do not mix domain documents with Python notes.
- Click **Assistant → Assistants → Create an assistant**
- Name it clearly: `civil-engineering-assistant` or `[your-domain]-assistant`
- Region: United States (default)

**2.3 — Select the model**
Click the Chat model dropdown and select **Claude Sonnet 4.5 — Anthropic**

**2.4 — Upload your domain documents**
Click the folder icon 📁 → click to upload → select all domain documents → wait for **Available** status on each file before proceeding.

> ⚠️ Do not test the assistant until all files show Available. Testing before indexing is complete produces unreliable answers.

## Step 3 — Write and Set the Domain System Prompt

The system prompt is the most important configuration step. It tells Claude how to behave — what to cite, when to refuse, and what the user is trying to do.

### The Generic System Prompt (Starting Point)

This is the system prompt used in the RAG module. Do not use it as-is for a domain application — it is too generic.

```text
You are an exam preparation assistant for a BTech AI programme.
Answer the student's question using only the lecture notes provided.
After each factual claim cite the source in square brackets — for example [Source 1].
If the notes do not contain enough information to answer the question,
say so clearly rather than guessing.
```

### The Civil Engineering System Prompt

Here is a domain-specific system prompt for the civil engineering knowledge assistant. Every line has a reason.

```text
You are a civil engineering standards reference assistant for BTech
civil engineering students in India.

Answer questions using only the uploaded IS codes, IRC standards,
and course notes. Do not use general engineering knowledge,
international standards (Eurocode, ACI, ASTM), or internet sources.

For every factual value, clause reference, or table entry you provide:
- Cite the source document in square brackets — for example [IS 456]
- Include the specific clause number or table number where available
  — for example [IS 456, Clause 26.4.2] or [IS 456, Table 16]

Do not perform calculations. If a question requires calculation,
provide the relevant formula and values from the uploaded standards
and state: "Apply this formula using the values above."

If the relevant standard has not been uploaded, state:
"The standard governing this topic ([standard name]) has not been
uploaded to this assistant. Please consult [standard name] directly."

If a question requires professional engineering judgment beyond
what the standard states, say:
"IS [code number] Clause [X] provides the general requirement
[Source 1]. Applying this to your specific case may require
interpretation by a licensed structural engineer."
```

### Your Domain System Prompt — Template

Adapt this template for your domain. The key elements that must appear in every domain system prompt:

```text
You are a [domain] [type of assistant] for [user type].

Answer questions using only the uploaded [document types].
Do not use [what to exclude — general knowledge, international
standards, internet sources, information not in the uploaded documents].

For every factual claim:
- Cite the source in square brackets — [Source name or number]
- Include [domain-specific reference — clause number / section /
  page / table / figure]

[Domain-specific limitation — what the AI should not do:
 calculate / diagnose / prescribe / advise / recommend]

If the relevant [document type] has not been uploaded:
[What to say]

If a question requires [professional judgment — engineering /
medical / legal / financial]:
[What to say — always direct to the human professional]
```

### Paste the System Prompt Into Pinecone

1. Click the ⚙️ gear icon in the playground
2. Find the **Assistant instructions** box
3. Paste your domain system prompt
4. The instructions apply immediately — no save button needed

## Step 4 — Build and Run the Golden Dataset

### Building the Golden Dataset

The golden dataset evaluation approach was covered in the RAG Failure and Recovery module. Apply it now to your domain application.

**10 questions, four types, in this ratio:**

| Type | Count | What it tests |
|---|---|---|
| Direct clause/value lookup | 4 | Can the chatbot find and cite the correct IS code value? |
| Comparison/relationship | 2 | Can it retrieve and connect content from multiple documents? |
| Out of scope | 2 | Does it correctly refuse questions outside the uploaded documents? |
| Edge case | 2 | Does it handle questions at the boundary of what the documents cover? |

**Civil engineering golden dataset — example:**

| # | Type | Question | Verified correct answer | Expected source |
|---|---|---|---|---|
| 1 | Direct | What is the minimum clear cover for a column in moderate exposure? | 40mm | IS 456, Table 16 |
| 2 | Direct | What is the characteristic compressive strength of M25 concrete? | 25 N/mm² | IS 456, Clause 6.1 |
| 3 | Direct | What is the permissible tensile stress in Fe 415 steel bars? | 230 N/mm² | IS 456, Annex B |
| 4 | Direct | What is the minimum eccentricity for a column under IS 456? | Greater of L/500 + D/30 or 20mm | IS 456, Clause 39.2 |
| 5 | Comparison | How does the Working Stress Method differ from the Limit State Method? | WSM uses permissible stresses; LSM considers collapse and serviceability limit states | IS 456 + Course notes |
| 6 | Comparison | What are the IS 456 requirements for both minimum and maximum reinforcement in a slab? | Min: 0.12% of gross area (Fe 415); Max: 4% of gross area | IS 456, Clause 26.5.2 |
| 7 | Out of scope | What does Eurocode 2 say about concrete cover? | Should refuse — Eurocode not uploaded | None |
| 8 | Out of scope | What is the history of the Bureau of Indian Standards? | Should refuse — not in uploaded documents | None |
| 9 | Edge case | What cover is required for a column in a coastal area? | Coastal = severe exposure — IS 456 Table 16 gives 50mm, but may require engineering judgment for specific site | IS 456, Table 16 |
| 10 | Edge case | Can I use M15 concrete for a reinforced concrete column? | IS 456 Clause 6.1 states M20 is minimum for RCC — but specific conditions apply | IS 456, Clause 6.1 |

> **Rule:** write the verified correct answer by reading the uploaded documents directly — not from memory and not from a general chatbot. The golden dataset is only reliable if the verified answers come from the actual source.

### Running the Evaluation

**Before fixes — baseline:**
1. Ask all 10 questions in the Pinecone playground
2. For each answer record: what the chatbot said, which source was cited, whether the citation is correct
3. Score each: Pass / Partial / Fail against your verified answer
4. Record your baseline score: X/10

**Apply fixes if needed:**
Use the failure mode analysis from the Common Failure Modes topic. If direct clause questions are failing — check that the IS code chunk is being retrieved correctly. If out-of-scope questions are not being refused — strengthen the system prompt refusal instruction.

**After fixes:**
Ask all 10 questions again. Record the post-fix answers. Score again.

**Evaluation record table:**

| # | Question | Verified answer | Chatbot answer before fix | Pass/Fail before | Fix applied | Chatbot answer after fix | Pass/Fail after |

**Minimum acceptable score:** 7/10 after fixes. If below 7 — diagnose the remaining failures using the hallucination patterns from the How RAG Hallucinates topic and apply additional fixes.

## Step 5 — Document and Submit A4

### What A4 Contains

A4 is the complete domain application submission. It has five components:

**Component 1 — Problem Statement**
Your completed problem statement from File 1. One page maximum. Includes: domain, users, knowledge base, what success looks like, what failure looks like.

**Component 2 — Design Document**
Your completed design document from File 2. Includes: five-stage workflow, failure analysis table, HITL model table, regulatory map.

**Component 3 — Pinecone Configuration**
Screenshots showing:
- Your assistant name and model (Claude Sonnet 4.5 selected)
- Your uploaded domain documents (all showing Available)
- Your domain system prompt in the Assistant instructions box
- One example answer with citation visible

**Component 4 — Evaluation Record**
Your completed evaluation record table — before and after scores. Includes the fix applied for any question that moved from Fail to Pass.

**Component 5 — Reflection**
300-400 words answering three questions:
1. Where did your application fail and what did that tell you about RAG's limitations in your domain?
2. Which oversight model did you apply to your highest-stakes question type and why?
3. Which regulatory framework creates the most significant obligation for your application and what does compliance require?

### A4 Submission Checklist

```text
☐ Problem statement completed — domain, users, knowledge base,
  success criteria, failure criteria

☐ Design document completed — workflow, failure analysis,
  HITL model, regulatory map

☐ Pinecone screenshots — assistant name, model, uploaded files,
  system prompt, one example answer with citation

☐ Golden dataset — 10 questions with verified correct answers
  written before running the chatbot

☐ Evaluation record — before score, fixes applied, after score

☐ Reflection — 300-400 words on failure, oversight model,
  regulatory obligation

☐ After score ≥ 7/10 — if below 7, diagnose and fix further
  before submitting
```

## Best Practices

- Write the golden dataset verified answers before running the chatbot — reading the IS code or domain standard yourself is the only way to know what the correct answer is
- Take the Pinecone screenshots for A4 as you build, not at the end — it is easier to capture each step as it happens than to recreate it later
- If a question scores Fail — diagnose the failure type using the hallucination patterns before applying a fix. Fixing without diagnosis means you might fix the wrong thing
- The reflection is where the learning is documented — be honest about failures. A reflection that says "everything worked perfectly" is not credible

## Common Beginner Mistakes

- **Uploading general textbooks instead of domain standards** — a RAG application built on a structural engineering textbook adds no value over a general chatbot. Upload the specific IS codes and course notes
- **Skipping the system prompt customisation** — the generic exam prep system prompt does not instruct Claude to cite clause numbers or refuse to calculate. The domain system prompt does. Using the wrong prompt produces generic answers
- **Writing golden dataset answers from memory** — the verified answer must come from the uploaded document. An answer from memory may differ from what the document actually says — which means the evaluation measures the wrong thing
- **Submitting with a score below 7/10** — a score below 7 means the application is not reliable enough for its stated purpose. Diagnose, fix, and re-evaluate before submitting

## Key Takeaways

- The build follows directly from the design — every configuration choice maps to something in the design document
- The domain system prompt is the most important configuration — it must specify what to cite, what not to do (calculate, use non-uploaded standards), and what to say when the relevant document is not uploaded
- The golden dataset verified answers must be written by reading the uploaded documents — not from memory or from a general chatbot
- A score of 7/10 or above after fixes is the minimum standard for a reliable domain application
- A4 has five components: problem statement, design document, Pinecone configuration screenshots, evaluation record, and a reflection

> **Interview tip:** If asked to describe a domain AI application you built — describe the problem statement (specific domain, specific documents, specific users), the system prompt design (what it constrains, what it refuses, what citations it requires), the evaluation approach (golden dataset, before and after scores), and one specific failure mode you discovered and fixed. Most candidates describe the tools they used. Describing the problem statement, the system prompt decisions, and a specific failure mode with its fix shows you understand domain AI deployment as a complete engineering process.
