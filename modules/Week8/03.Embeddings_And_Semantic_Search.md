# Embeddings and Semantic Search

## The Problem This Solves

The retry wrapper built in the previous file — `call_api_with_retry()` — makes the API calls reliable. But there is still a gap in the chatbot's design.

When a student types *"how does the algorithm learn from its mistakes?"*, the chatbot needs to find the relevant lecture notes before it can generate an answer. The obvious approach is to search for notes that contain those words.

The problem: the lecture notes never use those exact words. They say *"gradient descent minimises the loss function iteratively"*. Keyword search finds nothing — the words do not match.

But the meaning matches. Both phrases are asking the same thing. The student and the lecture notes are describing the same concept using different vocabulary.

This is the gap that **embeddings** fill. An embedding converts text into a list of numbers that represents its meaning — not its exact words. Two pieces of text with similar meaning get numbers that are close together. Two pieces of text with completely different meaning get numbers that are far apart.

With embeddings, *"how does the algorithm learn from its mistakes?"* and *"gradient descent minimises the loss function iteratively"* will be found as similar — because their meaning is similar, even though their words are not.

**Quick glossary:**

| Term | Meaning |
|---|---|
| **Embedding** | A list of numbers that represents the meaning of a piece of text |
| **Vector** | Another word for a list of numbers — used interchangeably with embedding |
| **Dimensions** | How many numbers are in the list — more dimensions capture more nuance |
| **Semantic search** | Searching by meaning — finds relevant content even with different words |
| **Keyword search** | Searching by exact word match — misses synonyms and paraphrases |
| **Cosine similarity** | A score from 0 to 1 showing how similar two embeddings are |
| **Embedding model** | The AI model that converts text into a vector |

## What an Embedding Is

A computer cannot understand the meaning of words directly — it only works with numbers. An embedding is the bridge: it converts a piece of text into a list of numbers in a way that preserves meaning.

Think of it like placing words on a map based on what they mean. Words with similar meaning end up close together on the map. Words with completely different meaning end up far apart.

```text
                    [machine learning map]

        neural network •  • deep learning
                          •
              gradient • • backpropagation
               descent

                                              • cooking
                                           • recipe
                                              • ingredients
```

"Neural network" and "deep learning" are close together — similar meaning. "Gradient descent" and "backpropagation" are close — both are optimisation concepts. "Cooking" and "recipe" are far from the machine learning cluster — completely different topic.

An embedding model does this automatically. You give it text. It gives you back a list of numbers — the coordinates of that text on the meaning map. The map has hundreds or thousands of dimensions instead of two, but the principle is identical.

## Keyword Search vs Semantic Search — Side by Side

The exam prep chatbot has lecture notes on gradient descent. A student types a question. Here is how keyword search and semantic search handle the same query:

**Student query:** *"how does the algorithm adjust when it gets something wrong?"*

**Lecture note:** *"Gradient descent calculates the error between the predicted and actual output, then adjusts the model's parameters in the direction that reduces that error."*

| | Keyword search | Semantic search |
|---|---|---|
| How it works | Looks for the exact words from the query in the notes | Converts both to embeddings, measures how close the numbers are |
| Finds this note? | ❌ No — "adjust", "algorithm", "wrong" do not appear | ✅ Yes — the meaning matches |
| Finds "gradient descent recipe"? | ✅ Yes — if both contain "gradient" | ❌ No — completely different meaning |
| Handles synonyms? | ❌ No | ✅ Yes |
| Handles paraphrasing? | ❌ No | ✅ Yes |

**When keyword search is better:**
- Searching for exact codes, IDs, or specific terms that must not be paraphrased
- Example: a student searching for "question 4b from 2024 paper" — exact match is what they want

**When semantic search is better:**
- Natural language questions where the words used may not match the document
- Finding conceptually related content across different phrasings
- Everything the exam prep chatbot does — students ask in their own words

## How Dimensions Work

Every embedding model produces vectors of a fixed size. That size is its **dimensionality** — the number of numbers in each vector.

```text
A 4-dimensional embedding (simplified for illustration):
"gradient descent" → [0.82, 0.14, 0.73, 0.05]

A real embedding from text-embedding-3-small:
"gradient descent" → [0.82, 0.14, 0.73, 0.05, 0.91, 0.33, 0.67, ...]
                      ← this list continues for 1,536 numbers total →
```

Each number captures a tiny fragment of meaning — is this text about optimisation? Is it mathematical? Is it introductory or advanced? Real models learn these dimensions automatically from billions of examples during training.

**Common embedding model sizes:**

| Model | Dimensions | Speed | Notes |
|---|---|---|---|
| `all-MiniLM-L6-v2` | 384 | Very fast | Free, runs locally, good for learning |
| `text-embedding-3-small` | 1,536 | Fast | OpenAI API — small cost per call |
| `text-embedding-3-large` | 3,072 | Slower | OpenAI API — higher quality, higher cost |

**The dimension mismatch rule — critical:**
All vectors being compared must come from the same embedding model. A 384-dimension vector from `all-MiniLM-L6-v2` cannot be compared to a 1,536-dimension vector from `text-embedding-3-small`. They are on completely different maps. Always use one model consistently throughout a project.

## Cosine Similarity — How Closeness Is Measured

Two embedding vectors are compared using **cosine similarity** — a score between 0 and 1:

- **Score close to 1** — very similar meaning
- **Score around 0.5** — somewhat related
- **Score close to 0** — completely unrelated

The score measures the angle between two vectors in the high-dimensional space — a small angle means they point in the same direction, meaning similar meaning. You do not need to calculate this by hand — the vector index in ChromaDB does it automatically for every stored document.

For the exam prep chatbot:

```text
Query: "how does the algorithm learn from mistakes?"

Compared against stored lecture notes:
"gradient descent minimises the loss function"     → similarity: 0.87  ✅ returned
"backpropagation computes gradients layer by layer" → similarity: 0.81  ✅ returned
"the softmax function normalises output probabilities" → similarity: 0.62 ✅ returned
"the French Revolution began in 1789"              → similarity: 0.04  ❌ not returned
```

The top three results are returned as context for the answer. The French history note is correctly ignored.

## Calling an Embedding Model

### Option 1 — Local Model with Sentence Transformers (Free, No API Key)

The `sentence-transformers` library runs embedding models directly on your machine — no API calls, no cost, no key needed. This is the best option for learning and development.

```bash
pip install sentence-transformers
```

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("all-MiniLM-L6-v2")
# downloads the model on first run (~90MB), cached locally after that

texts = [
    "gradient descent minimises the loss function iteratively",
    "backpropagation computes gradients layer by layer",
    "how does the algorithm learn from its mistakes?"
]

embeddings = model.encode(texts)

print(f"Number of texts embedded: {len(embeddings)}")
print(f"Dimensions per embedding: {len(embeddings[0])}")
print(f"First 5 numbers of embedding 0: {embeddings[0][:5]}")
```

**Output**

```text
Number of texts embedded: 3
Dimensions per embedding: 384
First 5 numbers of embedding 0: [ 0.0821 -0.0432  0.1204  0.0567 -0.0891]
```

`model.encode()` accepts a list of strings and returns a list of vectors — one vector per string. Processing multiple texts at once in a batch is faster than embedding them one at a time.

### Option 2 — OpenAI Embedding API

For production use where higher quality embeddings are needed:

```bash
pip install openai
```

```python
from openai import OpenAI
from dotenv import load_dotenv
import os

load_dotenv()

client = OpenAI(api_key=os.environ.get("OPENAI_API_KEY"))

texts = [
    "gradient descent minimises the loss function iteratively",
    "backpropagation computes gradients layer by layer",
    "how does the algorithm learn from its mistakes?"
]

response = client.embeddings.create(
    model="text-embedding-3-small",
    input=texts
)

embeddings = [item.embedding for item in response.data]

print(f"Number of texts embedded: {len(embeddings)}")
print(f"Dimensions per embedding: {len(embeddings[0])}")
```

**Output**

```text
Number of texts embedded: 3
Dimensions per embedding: 1536
```

The OpenAI embedding API call also needs the retry wrapper from the Rate Limits and Error Handling file — it is the same pattern as the Anthropic API call, just a different endpoint and client library.

## Embedding the Exam Prep Documents

The chatbot has three types of documents — lecture notes, past exam papers, and model answers. Each needs to be embedded before it can be searched.

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("all-MiniLM-L6-v2")

documents = [
    {
        "text": "Gradient descent is an optimisation algorithm that minimises the loss function by adjusting model parameters iteratively.",
        "type": "lecture_note",
        "subject": "machine_learning",
        "topic": "gradient_descent"
    },
    {
        "text": "Backpropagation calculates gradients layer by layer using the chain rule to update network weights.",
        "type": "lecture_note",
        "subject": "machine_learning",
        "topic": "backpropagation"
    },
    {
        "text": "Q4b (2024): Describe the role of the learning rate in gradient descent. What happens if it is set too high or too low?",
        "type": "past_paper",
        "subject": "machine_learning",
        "topic": "gradient_descent"
    },
    {
        "text": "A4b: A high learning rate causes the algorithm to overshoot the minimum. A low learning rate causes very slow convergence.",
        "type": "model_answer",
        "subject": "machine_learning",
        "topic": "gradient_descent"
    }
]

texts = [doc["text"] for doc in documents]
embeddings = model.encode(texts)

print(f"Embedded {len(embeddings)} documents")
print(f"Each vector has {len(embeddings[0])} dimensions")
```

**Output**

```text
Embedded 4 documents
Each vector has 384 dimensions
```

Each document now has a corresponding vector. The metadata — `type`, `subject`, `topic` — stays with the document and will be stored alongside the vector in ChromaDB, enabling filtered search.

## Checking Similarity Manually

Before storing in an index, it is useful to verify that the embeddings actually capture the right meaning:

```python
from sentence_transformers import SentenceTransformer, util

model = SentenceTransformer("all-MiniLM-L6-v2")

query = "how does the algorithm adjust when it gets something wrong?"

note_1 = "Gradient descent minimises the loss function by adjusting parameters."
note_2 = "The French Revolution began in 1789."

query_emb = model.encode(query)
note_1_emb = model.encode(note_1)
note_2_emb = model.encode(note_2)

sim_1 = util.cos_sim(query_emb, note_1_emb).item()
sim_2 = util.cos_sim(query_emb, note_2_emb).item()

print(f"Query vs gradient descent note: {sim_1:.3f}")
print(f"Query vs French Revolution note: {sim_2:.3f}")
```

**Output**

```text
Query vs gradient descent note: 0.847
Query vs French Revolution note: 0.031
```

`0.847` — the query and the gradient descent note are highly similar in meaning, even though the words are completely different.
`0.031` — the French Revolution note is essentially unrelated, as expected.

This manual check confirms the embedding model is working correctly before the vectors are stored in the index. In ChromaDB, this similarity calculation happens automatically for every stored document every time a student asks a question.

## Common Mistakes

- **Mixing embedding models** — comparing a 384-dimension vector from `all-MiniLM-L6-v2` to a 1,536-dimension vector from `text-embedding-3-small` will raise an error or produce meaningless results. Always use one model consistently throughout the project.
- **Embedding one text at a time in a loop** — `model.encode(texts)` with a list is significantly faster than calling `model.encode(text)` in a loop. Always batch.
- **Not storing metadata alongside the vector** — a vector alone is useless without knowing which document it came from. Always keep the original text and metadata (type, subject, topic) together with the vector.
- **Using keyword search where semantic search is needed** — if students ask questions in their own words, exact string matching will fail. Embed both the query and the documents.
- **Expecting similarity scores to always be high** — a score of 0.6 can still be the best match available. Always retrieve top-k results and let the LLM judge relevance from the content, not just the score.
- **Re-embedding documents every time the program runs** — documents only need to be embedded once. Store the vectors in the ChromaDB index so they persist between runs.
