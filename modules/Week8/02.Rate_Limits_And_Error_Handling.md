# Rate Limits and Error Handling

## Building on REST and Authentication

The previous file built `ask_chatbot()` — a function that takes a student's question and the retrieved lecture notes, sends both to the Anthropic API, and returns a generated answer. The key is loaded safely from `.env`, the headers are correct, and the request reaches the server.

That function works perfectly when one student uses the chatbot during a quiet afternoon. But consider what happens the night before the Data Science paper — 300 students all open the chatbot at the same time, all asking questions about gradient descent, probability, and neural networks.

The Anthropic API cannot serve unlimited requests simultaneously. It enforces **rate limits** — a cap on how many requests can be made per minute. When that cap is hit, the API stops accepting new requests and returns an error instead of an answer. If `ask_chatbot()` is not built to handle this, every student beyond the limit sees a crash instead of help.

Beyond rate limits, other things go wrong with API calls. A request might be malformed. The API key might be wrong. The server might have a temporary problem. Each failure is different and needs a different response.

This file covers two things: understanding what each error means, and wrapping `ask_chatbot()` in a retry system that handles failures automatically so students never see a raw error message.

**Quick glossary:**

| Term | Meaning |
|---|---|
| **Rate limit** | A cap on how many requests can be made in a given time window |
| **RPM** | Requests Per Minute — how many API calls allowed per minute |
| **TPM** | Tokens Per Minute — how many tokens can be processed per minute |
| **429** | The HTTP status code meaning "Too Many Requests" |
| **Retry** | Trying the same request again after a failure |
| **Exponential backoff** | Waiting progressively longer between retries — 1s, 2s, 4s, 8s |
| **Jitter** | Adding a small random delay to backoff — prevents all clients retrying at the same moment |
| **Idempotent** | Safe to retry — calling it twice gives the same result as calling it once |

## Understanding Rate Limits

### What Rate Limiting Means

Think of a busy café with one barista. The barista can make 10 coffees per minute. If 30 customers place orders at the same time, the barista does not try to make all 30 at once — that would make every coffee bad. Instead, the café accepts 10 orders per minute and asks the rest to wait.

The Anthropic API works the same way. It has a fixed capacity per account per minute. Once that capacity is used up, new requests get a `429 Too Many Requests` response instead of an answer — until the next minute window opens.

For the exam prep chatbot, two limits apply simultaneously:

| Limit type | What it counts | What triggers it |
|---|---|---|
| **RPM — Requests Per Minute** | Number of API calls | Sending too many messages per minute |
| **TPM — Tokens Per Minute** | Total tokens across all calls | Sending very long lecture notes repeatedly |

Both limits exist independently. Even if the number of requests is within the RPM limit, sending very long lecture notes in every request could hit the TPM limit first.

### Checking Your Limits

Every API response includes rate limit headers that tell you exactly where you stand:

```python
import requests
import os
from dotenv import load_dotenv

load_dotenv()

response = requests.post(
    "https://api.anthropic.com/v1/messages",
    headers={
        "Content-Type": "application/json",
        "x-api-key": os.environ.get("ANTHROPIC_API_KEY"),
        "anthropic-version": "2023-06-01"
    },
    json={
        "model": "claude-sonnet-4-6",
        "max_tokens": 100,
        "messages": [{"role": "user", "content": "What is gradient descent?"}]
    }
)

print("Requests remaining:", response.headers.get("x-ratelimit-requests-remaining"))
print("Tokens remaining:",   response.headers.get("x-ratelimit-tokens-remaining"))
print("Resets at:",          response.headers.get("x-ratelimit-requests-reset"))
```

**Output**

```text
Requests remaining: 47
Tokens remaining:   89432
Resets at:          2026-08-27T10:45:00Z
```

"Requests remaining: 47" means 47 more requests can be made before the minute window resets. The chatbot can read this header after every call and slow down proactively — before hitting zero — rather than waiting for a 429 to arrive.

## The Error Taxonomy — What Each Status Code Means

Not all errors are the same. Some mean "wait and try again." Others mean "fix your code before trying again." Knowing which is which prevents wasting retries on errors that will never succeed.

| Status code | Name | What happened | Should you retry? |
|---|---|---|---|
| `200` | OK | Success | — |
| `201` | Created | POST succeeded | — |
| `400` | Bad Request | The request body is malformed — wrong JSON, missing required field | ❌ No — fix the request first |
| `401` | Unauthorised | API key is missing or wrong | ❌ No — fix the key first |
| `403` | Forbidden | Key exists but account has no permission for this | ❌ No — check the account |
| `404` | Not Found | The endpoint URL is wrong | ❌ No — fix the URL first |
| `422` | Unprocessable | Valid JSON but the content is wrong — e.g. invalid model name | ❌ No — fix the payload first |
| `429` | Too Many Requests | Rate limit hit | ✅ Yes — wait then retry |
| `500` | Internal Server Error | Problem on the API's end | ✅ Yes — retry with backoff |
| `502` | Bad Gateway | Server overloaded or restarting | ✅ Yes — retry with backoff |
| `503` | Service Unavailable | API temporarily down | ✅ Yes — retry with backoff |

**The rule is simple:** `4xx` errors (except `429`) mean the request itself is wrong — fix it before retrying. `429` and `5xx` errors mean something outside your control went wrong — wait and retry.

For the exam prep chatbot, a `401` during the exam night rush means someone changed the API key. No amount of retrying will fix it — the key needs to be corrected in the `.env` file.

## Building a Retry System

### Why a Simple Retry Loop is Dangerous

The most naive retry looks like this:

```python
# dangerous — do not do this
while True:
    response = requests.post(...)
    if response.status_code == 200:
        break
```

If the API is rate-limiting because 300 students are sending requests, and every one of those 300 students retries immediately — the server gets hit with 300 requests again instantly. This makes the rate limit problem worse, not better. The server gets more overloaded, not less.

This is called the **thundering herd problem** — when a large number of clients all fail at the same moment and all retry at the same moment, they overwhelm the server in waves.

The fix is **exponential backoff** — waiting progressively longer between each retry attempt.

### Exponential Backoff — The Right Way to Retry

```text
Attempt 1 fails → wait 1 second  → Attempt 2
Attempt 2 fails → wait 2 seconds → Attempt 3
Attempt 3 fails → wait 4 seconds → Attempt 4
Attempt 4 fails → wait 8 seconds → Attempt 5
Attempt 5 fails → give up, raise the error
```

Each wait time doubles. This gives the server time to recover and spreads out the retry attempts so they do not all hit at once.

Think of it like a train station when all trains are delayed. If every passenger rushes to the information desk at the same time, the desk is overwhelmed and nobody gets helped. If passengers wait progressively longer before trying again, the queue clears and everyone eventually gets their information.

### Adding Jitter

Even with exponential backoff, if 300 students all start retrying at the same time they will still hit the server in synchronised waves — just slower ones. **Jitter** adds a small random amount to each wait time so that different students' retries land at different moments:

```text
Without jitter: all 300 retry at exactly t=1s, then t=2s, then t=4s
With jitter:    students retry at t=0.8s, t=1.1s, t=0.9s, t=1.3s...
```

The randomness breaks the synchronisation. The server sees a smooth trickle of retries instead of waves.

### The Complete Retry Function

```python
import requests
import time
import random
import os
from dotenv import load_dotenv

load_dotenv()

def call_api_with_retry(question: str, context: str, max_attempts: int = 5) -> str:
    # max_attempts: how many times to try before giving up

    api_key = os.environ.get("ANTHROPIC_API_KEY")
    if not api_key:
        raise ValueError("ANTHROPIC_API_KEY not set — check your .env file")

    for attempt in range(1, max_attempts + 1):
        # attempt goes 1, 2, 3, 4, 5

        try:
            response = requests.post(
                "https://api.anthropic.com/v1/messages",
                headers={
                    "Content-Type": "application/json",
                    "x-api-key": api_key,
                    "anthropic-version": "2023-06-01"
                },
                json={
                    "model": "claude-sonnet-4-6",
                    "max_tokens": 1024,
                    "system": (
                        "You are an exam preparation assistant. "
                        "Answer using only the lecture notes provided."
                    ),
                    "messages": [
                        {
                            "role": "user",
                            "content": f"Lecture notes:\n{context}\n\nQuestion: {question}"
                        }
                    ]
                },
                timeout=30
                # timeout=30 means: if no response arrives within 30 seconds, stop waiting
                # without a timeout, a slow server can hang the program forever
            )

            if response.status_code == 200:
                # success — return the answer immediately
                return response.json()["content"][0]["text"]

            elif response.status_code == 429:
                # rate limited — check if the server told us how long to wait
                retry_after = response.headers.get("Retry-After")

                if retry_after:
                    wait = float(retry_after)
                    print(f"Rate limited. Server says wait {wait}s. (Attempt {attempt}/{max_attempts})")
                else:
                    # server did not say — use exponential backoff with jitter
                    wait = (2 ** (attempt - 1)) + random.uniform(0, 1)
                    # 2 ** 0 = 1, 2 ** 1 = 2, 2 ** 2 = 4, 2 ** 3 = 8 ...
                    # random.uniform(0, 1) adds between 0 and 1 second of jitter
                    print(f"Rate limited. Waiting {wait:.1f}s before retry. (Attempt {attempt}/{max_attempts})")

                if attempt < max_attempts:
                    time.sleep(wait)

            elif response.status_code in (500, 502, 503):
                # server error — retry with backoff
                wait = (2 ** (attempt - 1)) + random.uniform(0, 1)
                print(f"Server error {response.status_code}. Waiting {wait:.1f}s. (Attempt {attempt}/{max_attempts})")

                if attempt < max_attempts:
                    time.sleep(wait)

            else:
                # 400, 401, 403, 404, 422 — do not retry, fix the request
                response.raise_for_status()
                # raise_for_status() raises an exception with the status code and reason
                # so the error is visible immediately instead of failing silently

        except requests.exceptions.Timeout:
            # the server took longer than 30 seconds to respond
            wait = (2 ** (attempt - 1)) + random.uniform(0, 1)
            print(f"Request timed out. Waiting {wait:.1f}s. (Attempt {attempt}/{max_attempts})")
            if attempt < max_attempts:
                time.sleep(wait)

        except requests.exceptions.ConnectionError:
            # no internet connection or server unreachable
            wait = (2 ** (attempt - 1)) + random.uniform(0, 1)
            print(f"Connection error. Waiting {wait:.1f}s. (Attempt {attempt}/{max_attempts})")
            if attempt < max_attempts:
                time.sleep(wait)

    # all attempts exhausted
    raise RuntimeError(f"API call failed after {max_attempts} attempts")


# Test it
question = "What is gradient descent?"
context  = (
    "Gradient descent is an optimisation algorithm that adjusts model parameters "
    "step by step to minimise the loss function."
)

answer = call_api_with_retry(question, context)
print(answer)
```

**Output** (when the first attempt succeeds)

```text
Gradient descent is an optimisation algorithm that minimises the loss function 
by adjusting model parameters step by step in the direction that reduces error.
```

**Output** (when rate limited on attempt 1)

```text
Rate limited. Waiting 1.4s before retry. (Attempt 1/5)
Gradient descent is an optimisation algorithm that minimises the loss function 
by adjusting model parameters step by step in the direction that reduces error.
```

The student sees the answer either way — just a short delay when the server is busy.

## What the Retry Logic Looks Like Step by Step

Walking through exactly what happens when 300 students query during the exam night:

```text
Attempt 1 → sends request → 429 returned → wait 1.3s (1s + 0.3s jitter)
Attempt 2 → sends request → 429 returned → wait 2.7s (2s + 0.7s jitter)
Attempt 3 → sends request → 200 returned → answer returned to student ✅
```

Most students get their answer on attempt 2 or 3. The progressive waiting means the server is not hammered repeatedly. The jitter means different students' retries land at different moments so the server sees a spread of requests rather than a synchronised wave.

## Using the Retry-After Header

When the API returns a `429`, it sometimes includes a `Retry-After` header telling you exactly how many seconds to wait:

```text
HTTP/1.1 429 Too Many Requests
Retry-After: 3
```

This is more reliable than calculating your own backoff — the server knows exactly when its rate limit window resets. The retry function above checks for this header first and only falls back to exponential backoff if it is missing.

## Logging Retries

In a real deployment, retries should be logged — not just printed — so the team can see patterns. If the chatbot is retrying on 40% of requests, the API tier needs upgrading. If retries are concentrated at 10pm before every exam, a request queue could smooth the load.

```python
import logging

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)

# replace print() with logger.warning() in the retry function:
logger.warning(f"Rate limited. Waiting {wait:.1f}s. (Attempt {attempt}/{max_attempts})")
```

Logs go to a file or monitoring system rather than the terminal, making patterns visible over time.

## Common Mistakes

- **Retrying on 4xx errors** — a `401` or `400` will never succeed with the same request. Retrying wastes time and burns through retry attempts. Only `429` and `5xx` errors should trigger a retry.
- **Not setting a timeout** — without `timeout=30`, a slow server holds the connection open indefinitely. The program appears frozen and the student sees nothing.
- **No maximum retry limit** — a retry loop without a `max_attempts` cap will keep retrying forever if the API is down for an extended period.
- **Immediate retry without waiting** — retrying instantly after a `429` makes the rate limit problem worse. Always wait before retrying.
- **Ignoring the `Retry-After` header** — when the server tells you exactly how long to wait, use that value. It is more accurate than a calculated backoff.
- **Swallowing exceptions silently** — catching an exception and doing nothing (`except: pass`) hides the error. Always log or re-raise so failures are visible.
